# Phase ২০ — লোড টেস্ট

## কীভাবে চালাবে

```bash
npm i --no-save autocannon
NODE_ENV=test node server.js &          # অথবা staging URL ব্যবহার করো
BASE_URL=http://localhost:4123 node scripts/loadTest.js
```

staging-এ:

```bash
BASE_URL=https://staging.example.com SPOOF_IPS=0 DURATION=60 CONNECTIONS=100 \
  node scripts/loadTest.js
```

স্ক্রিপ্টটা শুধু GET পাবলিক রুটে লোড দেয় — কোনো রাইট, লগইন বা পেমেন্ট নয়,
তাই staging-এও চালানো নিরাপদ।

## ⚠️ এই সংখ্যাগুলো কতটা বিশ্বাসযোগ্য

**এগুলো staging-এর ফল নয়।** পুরোটা একটা কন্টেইনারে চলেছে যেখানে অ্যাপ,
Postgres আর লোড জেনারেটর একই CPU ভাগ করেছে, Redis বন্ধ ছিল (কিউ inline
মোডে), আর ডেটাবেসে টেস্ট ডেটা ছাড়া কিছু ছিল না। তাই:

- **আপেক্ষিক তুলনায়** কাজে লাগে (কোন রুট ভারী, কনকারেন্সি বাড়লে কী হয়)
- **absolute ক্ষমতার** হিসেব হিসেবে ধরা যাবে না — আসল ক্যাপাসিটি পরিমাপ
  করতে হলে আলাদা staging পরিবেশ লাগবে, যেটা এখনো নেই

## রেট-লিমিটার সংক্রান্ত একটা জরুরি বিষয়

প্রথম রানে প্রতিটা রুটে **১০০% রিকোয়েস্ট ৪২৯** পেয়েছিল। কারণ
`app.js`-এর `generalLimiter` প্রতি IP-তে **১৫ মিনিটে ৩০০** রিকোয়েস্ট
অনুমোদন করে, আর একটা মেশিন থেকে লোড দিলে সব রিকোয়েস্ট একই IP।

অর্থাৎ IP স্পুফ না করলে লোড টেস্ট অ্যাপের গতি মাপে না — রেট-লিমিটারের গতি
মাপে। `scripts/loadTest.js` তাই প্রতি রিকোয়েস্টে আলাদা `X-Forwarded-For`
পাঠায় (`app.js`-এ `trust proxy = 1`, তাই ওটাই ক্লায়েন্ট কী)। staging-এ
লিমিটারসহ আচরণ দেখতে চাইলে `SPOOF_IPS=0` দাও।

পাশাপাশি এটা একটা পরিচালনাগত প্রশ্নও তোলে: NAT-এর পেছনে থাকা অনেক
ব্যবহারকারী (মোবাইল অপারেটর, অফিস, ক্যাফে) একই পাবলিক IP ভাগ করে। ১৫
মিনিটে ৩০০ তাদের জন্য যথেষ্ট কি না, সেটা আলাদা করে ভাবা দরকার — এই টেস্ট
সেটার উত্তর দেয় না, শুধু প্রশ্নটা সামনে আনে।

## ফলাফল — রুটভিত্তিক

২৫ কানেকশন, ১০ সেকেন্ড, per-request IP rotation চালু:

| রুট | req/sec | p50 (ms) | p95 (ms) | p99 (ms) | non-2xx |
|---|---|---|---|---|---|
| `/` | 170 | 137 | 235 | 261 | 0 |
| `/login` | 226 | 104 | 162 | 171 | 0 |
| `/register` | 229 | 105 | 150 | 162 | 0 |
| `/matches` | 290 | 81 | 132 | 150 | 0 |
| `/health` | 610 | 37 | 72 | 90 | 0 |

সব রুট থ্রেশহোল্ডের ভেতরে (`scripts/loadTest.js`-এ সংজ্ঞায়িত)।

## ফলাফল — কনকারেন্সি বাড়ালে (`/`)

| কানেকশন | req/sec | p50 (ms) | p95 (ms) | p99 (ms) |
|---|---|---|---|---|
| 10 | 188 | 50 | 99 | 105 |
| 50 | 169 | 280 | 384 | 389 |
| 100 | 178 | 544 | 807 | 1296 |
| 200 | 159 | 1081 | 4309 | 4825 |

পড়ার মতো বিষয়: **থ্রুপুট ১৭০–১৯০ req/sec-এ আটকে যায়**, কানেকশন বাড়ালেও
বাড়ে না — শুধু লেটেন্সি বাড়ে (কিউয়িং)। অর্থাৎ ১০ কানেকশনেই সার্ভিসটা
স্যাচুরেটেড, বাকিটা শুধু অপেক্ষা। কোনো এরর বা ড্রপ হয়নি, তাই ব্যাকপ্রেশার
আচরণ ভদ্র — ভেঙে পড়ে না, ধীর হয়।

এই সীমাটা এই কন্টেইনারের CPU-র, না অ্যাপের — সেটা এখান থেকে বলা যাবে না।
staging পেলে প্রথম কাজ হবে একই সুইপ চালিয়ে দেখা সংখ্যাটা কোথায় দাঁড়ায়।

## যা এখনো মাপা হয়নি

- লেখার পথ (ডিপোজিট, বাজি) — লোড দিলে আসল ডেটা তৈরি হত, তাই বাদ
- লগইন-পরবর্তী পেজ — সেশন লাগে, লোড হারনেসে এখনো নেই
- Redis চালু অবস্থায় কিউ আচরণ
- দীর্ঘ সময়ের সহনশীলতা (soak test), মেমরি লিক
