# bank_cards.holder_name ক্লিনআপ (মালিকের জন্য ধাপে ধাপে)

**কেন:** কার্ড-যোগ ফর্মের "পাসওয়ার্ড" ঘরের মান `bank_cards.holder_name`-এ সাধারণ টেক্সটে জমা হতো। এই স্ক্রিপ্ট সেগুলো সরিয়ে ফেলে এবং আক্রান্ত ইউজারদের পাসওয়ার্ড বদলাতে বাধ্য করে।
স্ক্রিপ্ট: `scripts/cleanupBankCardHolderName.js` — **কোনো ডেটা (নাম/মান/ইউজার আইডি/DB URL) লগে বা আউটপুটে ছাপে না, শুধু সংখ্যা।**

## ধাপ
1. **আগে staging-এ** (staging DB-র `DATABASE_URL` দিয়ে) চালান। প্রোডাকশনে সরাসরি নয়।
2. নতুন কোড ডিপ্লয় হয়ে migration চলেছে কি না দেখুন (`users.must_reset_password` কলাম তৈরি হয়; স্ক্রিপ্ট নিজেও `IF NOT EXISTS` দিয়ে নিশ্চিত করে)। **`--apply`-এর আগে নতুন কোড ডিপ্লয় থাকতে হবে**, নইলে ফ্ল্যাগ বসলেও কেউ আটকাবে না (শুধু সেশন বাতিল হবে)।
3. Render Shell-এ (বা `DATABASE_URL` সেট করা টার্মিনালে) **DRY-RUN** (ডিফল্ট — কিছুই বদলায় না):
   `node scripts/cleanupBankCardHolderName.js`
   আউটপুট: `আক্রান্ত row: N, আক্রান্ত ইউজার: M`
4. সংখ্যা যুক্তিসংগত হলে ডেটাবেসের একটি ব্যাকআপ/স্ন্যাপশট নিন, তারপর:
   `node scripts/cleanupBankCardHolderName.js --apply`
   এটি একটাই ট্রানজ্যাকশনে: ব্যাকআপ টেবিল `bank_cards_holder_name_backup`-এ কপি → `holder_name` ফাঁকা (NULL) → আক্রান্ত ইউজারের `must_reset_password=true`। ব্যর্থ হলে সব rollback।
   commit-এর পর পুরনো সেশন বাতিল হয় (বিদ্যমান `revokeAllOtherSessions` + Redis সেশন স্টোরে `livo:sess:*`)।
5. যাচাই: আবার dry-run চালান → `আক্রান্ত row: 0` আসতে হবে। আক্রান্ত ইউজার লগইন করলে পাসওয়ার্ড-বদল পাতায় যাবে; বদলালেই ফ্ল্যাগ মুছে যায়।
6. ⚠️ ব্যাকআপ টেবিলে পুরনো (সংবেদনশীল) মান আছে। অ্যাক্সেস সীমিত রাখুন, প্রয়োজন শেষে (যেমন ৭–৩০ দিন পর, মালিকের সিদ্ধান্তে) `DROP TABLE bank_cards_holder_name_backup;` দিয়ে মুছুন।
7. ⚠️ আক্রান্ত ইউজার যদি অন্য সাইটেও একই পাসওয়ার্ড ব্যবহার করে থাকেন, তাঁদের জানানোর সিদ্ধান্ত মালিকের।

## সীমাবদ্ধতা
- "আক্রান্ত" = `holder_name` অ-ফাঁকা এমন প্রতিটি row (নাম আর পাসওয়ার্ড আলাদা করা সম্ভব নয়)। `/profile/security/bank` ফর্মে যোগ করা বৈধ নামও ফাঁকা হবে (ব্যাকআপ থেকে ফেরত মেলে)।
- ফর্ম ও রুট এখন ঠিক করা আছে (নিচে "K2: holder_name ভ্যালিডেশন")।

## ব্যাকআপ টেবিল `bank_cards_holder_name_backup`: কে পড়তে পারে, এক্সপোজার, কবে/কীভাবে মুছবেন
- **আগে থেকে থাকলে** `--apply` থেমে যায় (exit 1; কিছু বদলায় না, সেশনও বাতিল হয় না; ওভাররাইট/ড্রপ/মার্জ নয়)। তাই একই স্ক্রিপ্ট আবার চালালে ব্যাকআপ হারায় না। পুরনো টেবিল যাচাই করে মালিক নিজে সরালে তবেই নতুন `--apply` চলবে।
- **কে পড়তে পারে:** যার ডাটাবেসে সরাসরি পড়ার অধিকার আছে (অ্যাপের DB ইউজার, Render/DB অ্যাডমিন)। অ্যাপের কোনো ইউজার-রুট বা অ্যাডমিন পেজ এই টেবিল পড়ে না (রিপোতে `bank_cards_holder_name_backup` শুধু স্ক্রিপ্টে আছে)। টেবিলে আলাদা কোনো এনক্রিপশন নেই — মান সাধারণ টেক্সটে।
- **⚠️ এক্সপোজার (কোডে যাচাই করা):**
  1. `services/backupManager.js`-এর `dumpAllTables()` `public`-এর **সব** টেবিল ডাম্প করে (শুধু `session` বাদ) — অর্থাৎ অ্যাডমিন প্যানেলের DB ব্যাকআপ ফাইলে এই ব্যাকআপ টেবিলও যাবে। ফাইল `BACKUP_DIR`-এ থাকে; `BACKUP_ENCRYPTION_KEY` সেট থাকলে AES-GCM, নইলে শুধু gzip (সাধারণ টেক্সট)। `backups_manage` অনুমতিধারী অ্যাডমিন ডাউনলোড করতে পারে। রিস্টোর শুধু `RESTORE_ORDER`-এর টেবিল ফেরায়, এই টেবিল নয়।
  2. **ক্লিনআপের আগে নেওয়া সব ব্যাকআপ ফাইল/DB স্ন্যাপশটে `bank_cards.holder_name`-এ পুরনো মানগুলো আগে থেকেই আছে** (এই ক্লিনআপ ওগুলো মোছে না)। হোস্টিং-প্রোভাইডারের স্বয়ংক্রিয় স্ন্যাপশটেও থাকবে।
  3. `--apply`-এর আগের "ডাটাবেসের ব্যাকআপ নিন" ধাপেও আক্রান্ত মান কপি হয়।
- **কখন মুছবেন (মালিকের সিদ্ধান্ত; প্রস্তাব):** আক্রান্ত ইউজাররা পাসওয়ার্ড বদলানোর পর এবং ক্লিনআপ যাচাইয়ের (dry-run → `আক্রান্ত row: 0`) পর, ৭–৩০ দিনের মধ্যে।
- **কীভাবে মুছবেন:** (ক) `DROP TABLE bank_cards_holder_name_backup;` (খ) এর আগের ও পরের অ্যাডমিন DB ব্যাকআপ ফাইলগুলো (অ্যাডমিন → Backups → Delete) ও হোস্টিং স্ন্যাপশট যতটা সম্ভব মেয়াদ শেষে/মুছে ফেলুন; যেগুলো রাখতেই হবে সেগুলোতে অ্যাক্সেস সীমিত ও এনক্রিপ্টেড রাখুন। (গ) মোছার তারিখ নিজের রেকর্ডে লিখে রাখুন।

## `users.must_reset_password` migration নিরাপত্তা (`ALTER TABLE users ADD COLUMN IF NOT EXISTS must_reset_password BOOLEAN NOT NULL DEFAULT false`)
- **NOT NULL DEFAULT false:** হ্যাঁ (টেস্টে কলামের তথ্য যাচাই করা)।
- **লক/রিরাইট:** Postgres ≥ 11-এ ধ্রুবক ডিফল্টসহ ADD COLUMN টেবিল রিরাইট করে না (টেস্টে ২০,০০০ সারিতে `relfilenode` অপরিবর্তিত); ALTER ট্রানজ্যাকশনে ক্ষণিকের জন্য `ACCESS EXCLUSIVE` লক ধরে (শুধু ক্যাটালগ বদল) — তাই চলমান দীর্ঘ কোয়েরি থাকলে লক পেতে অপেক্ষা হতে পারে; কম ট্রাফিকে চালান। প্রোডাকশন Postgres-এর সংস্করণ এখানে যাচাই করা যায়নি → `SHOW server_version_num` ≥ 110000 কিনা দেখে নিন।
- **Idempotent:** `IF NOT EXISTS` — বারবার চালালে একই; ডেটা বদলায় না (টেস্টে যাচাই)। ক্লিনআপ স্ক্রিপ্টও একই বাক্য ব্যবহার করে।
- **পুরনো কোডের সঙ্গে সামঞ্জস্য:** পুরনো কোড কলাম জানে না; তার INSERT-এ ডিফল্ট `false` বসে, SELECT অক্ষত (টেস্টে যাচাই)। ফ্ল্যাগ `true` থাকা ইউজারকে **পুরনো কোড আটকাবে না** — তাই `--apply` শুধু নতুন কোড ডিপ্লয়ের পরে চালান।
- **Rollback:** কোড আগে ফেরান, তারপর (দরকারে) `ALTER TABLE users DROP COLUMN must_reset_password;` — পুরনো কোয়েরি চলে (টেস্টে যাচাই)। কলাম ফেললে ফ্ল্যাগের তথ্য হারায়; ফেলার আগে `SELECT id FROM users WHERE must_reset_password` সংরক্ষণ করুন।

## `isAuth` গার্ড
- বাড়তি DB কোয়েরি নেই: কলামটি বিদ্যমান স্ট্যাটাস কোয়েরির সঙ্গে (`SELECT is_banned, self_exclude_until, must_reset_password`) আসে, ৩০ সেকেন্ড ক্যাশে; প্রতি রিকোয়েস্টে ঠিক ১টি কোয়েরি (ক্যাশ মিসে)।
- ফ্ল্যাগধারী পারে: পাসওয়ার্ড বদল (`/profile/security/login-password`, `/profile/change-password`), টোকেন-রিসেট (`/reset-password/:token`, isAuth-এর বাইরে), লগআউট, লগইন। পারে না: বাজি, ওয়ালেট/ব্যালেন্স, উত্তোলন, কার্ড, প্রোফাইল ও বাকি সব (রিডাইরেক্ট; `/api/` পথে 403 JSON)। ফ্ল্যাগ পরিষ্কার হলে (পাসওয়ার্ড বদল/রিসেটে ক্যাশ মুছে) সব ফেরে। আলাদা "প্রোফাইল-স্ট্যাটাস" endpoint রিপোতে পাইনি।
- ডিপ্লয়ের সময় ক্যাশে থাকা পুরনো এন্ট্রিতে ফ্ল্যাগ থাকে না — সর্বোচ্চ ৩০ সেকেন্ড গার্ড দেরিতে কার্যকর হতে পারে।

## K2: holder_name ভ্যালিডেশন
- নিয়ম: শুধু Unicode অক্ষর (বাংলা স্বরচিহ্নসহ), স্পেস, ডট, হাইফেন, অ্যাপোস্ট্রফি; ২–৬০ অক্ষর। অঙ্ক/অন্য চিহ্ন/ইমপোর্ট-করা পাসওয়ার্ড-সদৃশ মান প্রত্যাখ্যাত। সাধারণ এরর (`holder_name_invalid`, bn/en); মান লগে/রেসপন্সে আসে না।
- সার্ভার (আসল গার্ড): `utils/holderName.js` — `POST /profile/add-bank-card`, `POST /profile/cards/add`, এবং ব্যাকআপ রিস্টোর/ইমপোর্ট (`bank_cards`-এ অবৈধ মান NULL, কার্ড সারি থাকে)। অ্যাডমিনের কোনো `holder_name` লেখার পথ রিপোতে নেই (টেস্ট নতুন অরক্ষিত পথ ধরবে)।
- ক্লায়েন্ট: `public/js/holder-name-validate.js` (সার্ভারের সমান নিয়ম, টেস্টে সমতা যাচাই); ফর্মে `type="text" autocomplete="name"` (পাসওয়ার্ড autofill বন্ধ)।
- সীমা: শুধু অক্ষরের পাসওয়ার্ড (যেমন `SecurePass`) নাম থেকে আলাদা করা অসম্ভব — আটকায় না।
